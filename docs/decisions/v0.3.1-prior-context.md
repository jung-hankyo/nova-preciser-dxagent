# Decision record: v0.3.1 prior context (decisions 20-22)

Date: 2026-10-01. Code: `dxagent` v0.3.1 (from v0.3.0). Continues decision records 1-19 of the design report.

## Context

Review of v0.3.0 found four problems with how the pretest prior is set at the start of a case:

1. Demographics are the weakest conditioning information; richer context (vital signs, occupation, past history and
   treatment, recent food or drug intake) should change the diagnostic probabilities.
2. "The prior conditions on the primary complaint only" was an instruction to the LLM, not a property of the code. The
   generator sees every finding and may use them, which would double count evidence with the update.
3. The primary complaint was the extractor's flag, falling back to the first present finding: no rule.
4. A five-level bucket chosen once by an LLM needs a safety net against a too-strong first prior (to be handled after
   measurement).

Code inspection added three facts: `perceive` extracted age and sex into `state["context"]` but no prompt read it; a
card's single `prevalence` bucket was drafted in whatever context first triggered the draft and reused under unrelated
complaints (so the reverse index could double count through it); and a disease's prior depended on how it entered the
list (the LLM's bucket for generator and critic proposals, the card's prevalence for reverse-index, veto and dissent
additions).

Decision on point 1: context is counted as **evidence through the cards**, not folded into the prior. Bayes is
indifferent to where a fact enters as long as it enters once; the evidence route is auditable, visible to the reverse
index, and does not repeat the failure fixed by A1. The real gap is coverage: a context fact moves the posterior only if
some card has an entry for it.

## Decision 20 (P1): the prior conditions on S, by construction

`DX_PRIOR_CONTEXT=1`, default on.

- **Prior context S** = {age, sex, care setting, complaint}, the only input a prior may use. Age, sex and setting are
  filled from any reply (first value wins); every bucket is reassigned whenever S changes.
- **Complaint registry** (`dxagent/knowledge/complaints.py`): LLM-normalized complaint labels that consolidate like finding
  codes (alias table; concept Dice at least 0.85 merges automatically; 0.60-0.85 one LLM confirmation), each with a
  typical triage acuity (KTAS/CTAS 1-5) assigned once and cached.
- **Primary-complaint rule** (`priors.select_complaint`): stated reason for the visit, then the most urgent acuity,
  then the earliest mention. Exactly that complaint's finding is excluded from the update. Severity is a tiebreak only:
  choosing by severity would move the most dangerous finding out of the auditable update into the prior.
- **Information-hidden prior assessor** (`priors.PriorService`): one LLM call shown only S and the disease names,
  sampled K = 3 times, median bucket; it assigns the bucket on every entry route; the proposer's bucket is logged as
  `proposed_bucket` and never used. The reverse index stays LLM-free.
- **Complaint-keyed prevalence** (`DiseaseCard.prevalence_by_complaint`): drafting asks for prevalence among patients
  with the complaint alone; the reverse index uses the keyed entry or 0.02. If the keyed bucket and the assessor differ
  by two or more buckets they meet in the middle; otherwise the assessor wins, since only it sees age, sex and setting.
- **Diagnostics in every final report:** `prior_sensitivity`, `context_coverage`, `prior_context`, `prior_log`.

**Measured effect** (`experiments/v03_sim.py`, real graph nodes, simulated LLM roles; development worlds 11-13, then
held-out worlds 21-30, 5,000 paired cases). `LEAK` is how far the generator ignores the instruction (a log-odds mix of
P(d | complaint) and P(d | complaint + every finding reported so far), computed with the agent's own cards).

| Generator, P1 minus v0.3 | Top-1 | Brier | Turns | Cost | LLM calls |
|---|---|---|---|---|---|
| Obeys the instruction | -0.1 pp [-0.6, +0.3] | +0.002 [-0.002, +0.005] | +0.00 | +$3 [-6, +12] | +5.5 |
| Ignores it fully | -0.5 pp [-1.0, 0.0] | **+0.004 [+0.001, +0.008]** | **+0.07** | **+$11 [+1, +21]** | +5.6 |

ECE and log loss do not move. K = 1 instead of 3 changes no quality metric and costs +1.9 instead of +5.7 calls. The
P1 arm gives identical results under every `LEAK` setting (information hiding verified), and the leak detector separates
the cases: the mean gap between the proposer's and the assessor's bucket is 0.31 buckets when the generator obeys and
1.11 when it leaks fully.

**Why there is no gain in simulation.** The prior rarely decides (under flat priors the leader changes in 1.6-1.9% of
cases), and the agent is underconfident (mean top-1 probability 0.900 against accuracy 0.930, below the diagonal in
every bin), so double counting sharpens an underconfident posterior instead of harming it.

**Verdict.** Fails the pre-registered acceptance rule (no gain; more LLM calls; worse against a fully leaking
generator). **Adopted, default on, by decision**, as E1 and F1 were: the prior is a function of S alone, verifiably,
whatever the generator does; leakage becomes measurable on the live run; and the simulated worlds are easier than
MedQA, where a prior may decide more often. Cost control: `DX_PRIOR_MODEL` (a small model suffices) and
`DX_PRIOR_SAMPLES=1`.

**Revisit after the live baseline** (`summary.json`): `prior_decides_flat`, `prior_leak_gap`,
`prior_vote_disagreement`, `complaint_rule`, `complaint_finding_match`. If the prior rarely decides and the leak gap is
small, drop to K = 1 or revert; if live calibration is also underconfident, fix calibration directly (card shrinkage,
extraction confidence) rather than relying on accidental double counting.

## Decision 21: context reaches the update as evidence

- **Vital signs** map to findings by registry thresholds, never by the LLM (`FindingDef.rules`, `apply_vital_rules`):
  heart_rate > 100, temperature_c > 38 or temperature_f > 100.4, resp_rate > 22, sbp < 90, spo2 < 92%. Units are never
  converted. The rule's finding (confidence 0.97) overrides the LLM's coding of the same code in the same turn.
- **Categories** on every registry finding (symptom, sign, vital, risk_factor, exposure, medication, family_history).
- **Card drafting** must include 3-6 risk factors, exposures or medications with frequencies; **extraction** codes every
  stated context fact and reports vital signs as numbers; the lexicon gains lay words for smoking and immobility.
- **Coverage metric** `context_coverage`: findings no top card explains, by arrival (opening and intake vs later),
  channel and category.

No effect in simulation, by construction (the simulator produces no vital signs or categories); unit-tested. Whether
context is being lost is the live coverage metric's question.

## Decision 22: deterministic simulation harness

Concurrent card drafting made identical runs of the original v0.3.0 package differ in 10 of 400 cases. `v03_sim.py` now
runs the package's thread pools serially: identical runs match exactly, and the v0.3 arm reproduces the original v0.3.0
package in 400/400 cases, including LLM call counts. Earlier v0.3 simulation numbers carry about 2.5% run-to-run noise;
none of their conclusions was close enough to change.

## Not done

Prior tempering and bucket recalibration beyond the diagnostic (needs live outcomes); seed entries for the new vital
codes and exposures; a Korean lexicon (added later for the contest); complaint acuity is a per-complaint simplification
of KTAS, which depends on modifiers.
